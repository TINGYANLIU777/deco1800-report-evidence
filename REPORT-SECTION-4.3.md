## 4.3 Resolving Technical and Design Problems

The Council datasets did not tell us how much social interaction each activity involved, so we developed rules to estimate this from the available information (Brisbane City Council, n.d.-a, n.d.-b). At first, the system checked titles, categories and descriptions and assigned a level based on the first keyword match. We reproduced a problem with this when a synthetic Zumba example was labelled as an independent activity because its description included “at your own pace”. This could give families the wrong idea about what to expect ([E01](source-before.txt); [E03](controlled-cases.json)).

We changed the system to consider clues from titles, categories and descriptions separately, generally giving more weight to titles and structured categories than to descriptions. This reduced the effect of phrases that did not describe the activity as a whole. Users can see which clues were used and how much evidence supports the rating. If there is too little information, or conflicting clues do not produce a clear result, the system gives a provisional L2 rating. In the later GitHub implementation, this uncertain social evidence is excluded from the internal preference-score calculation, rather than counted as a confirmed mismatch ([E02](source-after.txt); [Figures 1–2](README.md#2-interface-evidence); [E09](source-matching.txt)).

We then tested two versions of the Zumba description and checked that the result remained L3. This showed that the change fixed the example we had identified. However, we still need to compare the ratings with human judgements and feedback from people who attended the activities. The description alone cannot tell us exactly how much interaction someone will experience ([E03](controlled-cases.json); [E04](test-results.txt)).
